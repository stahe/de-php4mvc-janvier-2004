    4. Ein anschauliches Beispiel

    Wir möchten die vorstehende Methode anhand eines Beispiels zur Steuerberechnung veranschaulichen.

    4.1. Die Aufgabe

    Wir wollen ein Programm schreiben, mit dem sich die Steuer eines Steuerpflichtigen berechnen lässt. Wir betrachten den vereinfachten Fall eines Steuerpflichtigen, der nur sein Gehalt anzugeben hat:

    • Wir berechnen die Anzahl der Steueranteile des Arbeitnehmers nbParts = nbEnfants/2 + 1, wenn er unverheiratet ist, nbEnfants/2+2, wenn er verheiratet ist, wobei nbEnfants die Anzahl seiner Kinder ist. Die Anzahl der Anteile wird um 0,5 erhöht, wenn drei oder mehr Kinder vorhanden sind.
    • Man berechnet sein zu versteuerndes Einkommen R = 0,72 * S, wobei S sein Jahresgehalt ist
    • Man berechnet seinen Familienkoeffizienten Q = R/N
    • Man berechnet seine Steuer I anhand der folgenden Daten

    4.3. Die Architektur MVC der Anwendung

    Die Anwendung wird die folgende Architektur „MVC“ aufweisen:

    • Der Controller main.php ist der zuvor vorgestellte generische Controller
    • Die Anfrage des Kunden wird in Form einer Anfrage mit dem Format main.php?action=xx an den Controller gesendet. Der Wert des Parameters „action“ bestimmt das auszuführende Skript des Blocks ACTIONS. Das ausgeführte Aktionsskript gibt dem Controller eine Variable zurück, die den Zustand angibt, in den die Webanwendung versetzt werden soll. Mit diesem Zustand aktiviert der Controller einen der View-Generatoren, um die Antwort an den Client zu senden.
    • impots-data.php ist die Klasse, die dem Controller die benötigten Daten bereitstellt
    • impots-calcul.php ist die Fachklasse, die die Berechnung der Steuer ermöglicht

    4.4. Die Datenzugriffsklasse

    Die Datenzugriffsklasse dient dazu, die Herkunft der Daten vor der Webanwendung zu verbergen. In ihrer Schnittstelle findet sich eine Methode getData, die die drei für die Steuerberechnung erforderlichen Datenarrays bereitstellt. In unserem Beispiel werden die Daten aus einer Datenbank MySQL abgerufen. Um die Klasse vom tatsächlichen Typ der Datenbank SGBD unabhängig zu machen, verwenden wir die im Anhang beschriebene Bibliothek pear::DB. Der Code der Klasse lautet wie folgt:

        var $sQuery ;      // die zuletzt ausgeführte Abfrage

     // Konstruktor
    function impots_data($dDSN){

         // $dDSN: Dictionary, das die herzustellende Verbindung definiert
       // $dDSN['sgbd']: der Typ des SGBD, mit dem eine Verbindung hergestellt werden soll
       // $dDSN['host']: Name des Host-Rechners, auf dem es gehostet wird      
       // $dDSN['database']: der Name der Datenbank, mit der eine Verbindung hergestellt werden soll      
       // $dDSN['user']: ein Benutzer der Datenbank
       // $dDSN['mdp']: sein Passwort

       // erstellt in $oDB eine Verbindung zur Datenbank, die durch $dDSN definiert ist, unter der Identität von $dDSN['user']
       // wenn die Verbindung erfolgreich hergestellt wurde  
           // speichert in $sDSN die Verbindungszeichenfolge zur Datenbank
           // speichert den Namen der Datenbank, mit der eine Verbindung hergestellt wird, in $sDataBase
         // setzt $connecté auf „wahr“
       // falls die Verbindung fehlschlägt
           // trägt die entsprechenden Fehlermeldungen in die Liste $aErreurs ein
         // schließt die Verbindung bei Bedarf
         // setzt $connecté auf „falsch“ 

       // löscht die Fehlerliste
            $this->aErreurs=array();

       // Es wird eine Verbindung zur Datenbank $sDSN hergestellt
      $this->sDSN=$dDSN["sgbd"]."://".$dDSN["user"].":".$dDSN["mdp"]."@".$dDSN["host"]."/".$dDSN["database"];
      $this->sDatabase=$dDSN["database"];
      $this->connect();

       // Verbunden?
      if( ! $this->connecté) return;

       // Die Verbindung wurde erfolgreich hergestellt     
      $this->connecté=TRUE;

    // ------------------------------------------------------------------
    function connect(){
         // (Wieder-)Verbindung zur Datenbank
       // Fehlerliste zurücksetzen
            $this->aErreurs=array();

       // Es wird eine Verbindung zur Datenbank hergestellt $sDSN
        $this->oDB=DB::connect($this->sDSN,true);

         // Fehler?
        if(DB::iserror($this->oDB)){
           // Fehler wird protokolliert
          $this->aErreurs[]="Echec de la connexion à la base [".$this->sDatabase."] : [".$this->oDB->getMessage()."]";
         // Die Verbindung ist fehlgeschlagen
        $this->connecté=FALSE;
         // Ende
        return;
      }

       // Verbindung hergestellt
      $this->connecté=TRUE;
    }//Verbinden

    // ------------------------------------------------------------------
    function disconnect(){
       // Wenn eine Verbindung besteht, wird die Verbindung zur Basisstation getrennt $sDSN
        if($this->connecté){
              $this->oDB->disconnect();
           // Man ist nicht verbunden
        $this->connecté=FALSE;
            }//if
    }//Verbindung trennen

    // -------------------------------------------------------------------
    function execute($sQuery){
         // $sQuery: auszuführende Abfrage

         // Die Anfrage wird gespeichert
            $this->sQuery=$sQuery;    

       // Sind wir angemeldet?
      if(! $this->connecté){
           // Der Fehler wird vermerkt
        $this->aErreurs[]="Pas de connexion existante à la base [$this->sDatabase]";
         // Ende
        return;
      }//if

       // Abfrage ausführen
      $this->oRésultats=$this->oDB->query($sQuery);

         // Fehler?
        if(DB::iserror($this->oRésultats)){
             // Der Fehler wird vermerkt
            $this->aErreurs[]="Echec de la requête [$sQuery] : [".$this->oRésultats->getMessage()."]";
           // Zurück
        return;
      }//if     
    }//ausführen

    // ------------------------------------------------------------------
    function getData(){
       // Die drei Datensätze „limites“, „coeffr“ und „coeffn“ werden abgerufen
      $this->execute('select limites, coeffR, coeffN from impots');
       // Gibt es Fehler?
      if(count($this->aErreurs)!=0) return array();
       // Das Ergebnis der SELECT-Anweisung wird durchlaufen
      while ($ligne = $this->oRésultats->fetchRow(DB_FETCHMODE_ASSOC)) {
        $limites[]=$ligne['limites'];
        $coeffr[]=$ligne['coeffR'];
        $coeffn[]=$ligne['coeffN'];                
      }//while
      return array($limites,$coeffr,$coeffn);      
    }//getDataImpots

  }//Klasse

    4.5. Die Klasse zur Steuerberechnung

    Diese Klasse dient zur Berechnung der Steuer eines Steuerpflichtigen. Dem Konstruktor werden die für diese Berechnung erforderlichen Daten übergeben. Anschließend berechnet er die entsprechende Steuer. Der Code der Klasse lautet wie folgt:

    <?php

  class impots_calcul{  
    // Steuerberechnungsklasse

    // Konstruktor
    function impots_calcul(&$perso,&$data){
      // $perso: Wörterbuch mit folgenden Schlüsseln
      // Kinder: Anzahl der Kinder
      // Gehalt: Jahresgehalt
      // verheiratet: Boolescher Wert, der angibt, ob der Steuerpflichtige verheiratet ist oder nicht
      // Steuer(n): von diesem Konstruktor berechnete zu zahlende Steuer
      // $data: Wörterbuch mit den folgenden Schlüsseln
      // Grenzen: Tabelle der Steuerklassengrenzen
      // Koeffizienten: Tabelle der Einkommenskoeffizienten
      // coeffn: Tabelle der Koeffizienten für die Anzahl der Anteile
      // Die drei Tabellen haben die gleiche Anzahl an Elementen

      // Berechnung der Anzahl der Anteile
      if($perso['marié'])
        $nbParts=$perso['enfants']/2+2;
        else $nbParts=$perso['enfants']/2+1;
      if ($perso['enfants']>=3) $nbParts+=0.5;

      // steuerpflichtiges Einkommen
      $revenu=0.72*$perso['salaire'];

      // Familienquotient
      $QF=$revenu/$nbParts;

      // Ermittlung der Steuerklasse entsprechend QF
      $nbTranches=count($data['limites']);
      $i=0;
      while($i<$nbTranches-2 && $QF>$data['limites'][$i]) $i++;

      // die Steuer
      $perso['impot']=floor($data['coeffr'][$i]*$revenu-$data['coeffn'][$i]*$nbParts);
    }//Ersteller
  }//Klasse
?>

    4.9. Die Aktionen der Webanwendung

    Es gibt vier Aktionen:

    • get:init: Diese Aktion wird bei der ersten Anfrage ohne Parameter an den Controller ausgelöst. Sie generiert die leere Ansicht „Formular“.
    • post:effacerformulaire: Diese Aktion wird durch die Schaltfläche [Effacer le formulaire] ausgelöst. Sie generiert die leere Ansicht [v-formulaire].
    • post:calculerimpot: Diese Aktion wird durch die Schaltfläche [Calculer l'impôt] ausgelöst. Sie generiert entweder die Ansicht [v-formulaire] mit dem zu zahlenden Steuerbetrag oder die Ansicht [v-erreurs].

    4.12. Aktionen der Webanwendung

    4.12.1. Allgemeine Funktionsweise von Aktionsskripten

    • Ein Aktionsskript wird vom Controller entsprechend dem Aktionsparameter aufgerufen, den dieser vom Client erhalten hat.
    • Nach der Ausführung muss das Aktionsskript dem Controller mitteilen, in welchen Status die Anwendung versetzt werden soll. Dieser Status muss in $dSession['etat']['principal'] angegeben werden.
    • Ein Aktionsskript möchte möglicherweise Informationen in die Sitzung einfügen. Dies geschieht, indem diese Informationen in das Wörterbuch $dSession eingefügt werden; dieses Wörterbuch wird am Ende des Anfrage-Antwort-Zyklus vom Controller automatisch in der Sitzung gespeichert.
    • Ein Aktionsskript kann Informationen an die Ansichten weitergeben. Dieser Aspekt ist unabhängig vom Controller. Es handelt sich um die Schnittstelle zwischen den Aktionen und den Ansichten, die für jede Anwendung spezifisch ist. Im hier betrachteten Beispiel stellen die Aktionen den Ansichtsgeneratoren Informationen über ein Dictionary namens $dReponse zur Verfügung.

    4.15.1. Die Rolle eines View-Generators

    Erinnern wir uns an den Codeabschnitt im Controller, der einen View-Generator ausführt:

    Wir haben bereits erläutert, welche Rolle ein View-Generator spielt. Lassen Sie uns dies hier noch einmal zusammenfassen. Ein View-Generator:

    • legt in $dReponse['vuereponse'] den Namen der zu verwendenden Antwortvorlage fest. Diese Information wird an den Controller weitergeleitet. Eine Vorlage ist eine Zusammensetzung aus Elementaransichten, die zusammen die endgültige Ansicht bilden.
    • bereitet die dynamischen Informationen vor, die in der endgültigen Ansicht angezeigt werden sollen. Dieser Schritt ist unabhängig vom Controller. Es handelt sich um die Schnittstelle zwischen dem View-Generator und der endgültigen Ansicht. Sie ist für jede Anwendung spezifisch.
    • muss zwingend mit dem Aufruf der Controller-Funktion finSession enden. Diese Funktion
      • die Sitzung speichern
      • die Antwort senden

    4.17. Fazit

    Anhand eines Beispiels konnten wir den Nutzen unseres generischen Controllers aufzeigen. Wir mussten diesen nicht selbst schreiben. Wir haben uns darauf beschränkt, die Skripte für die Aktionen, die View-Generatoren und die Views der Anwendung zu schreiben. Außerdem haben wir den Vorteil der Trennung von Aktionen und Views aufgezeigt. So konnten wir das Erscheinungsbild der Antworten ändern, ohne auch nur eine einzige Zeile Code in den Aktionsskripten zu ändern. Nur die Skripte, die an der Generierung der Ansichten beteiligt sind, wurden geändert. Damit dies möglich ist, darf das Aktionsskript keinerlei Annahmen über die Ansicht treffen, die die von ihm berechneten Informationen anzeigen wird. Es muss sich darauf beschränken, diese Informationen an den Controller zu übergeben, der sie an den Ansichtsgenerator weiterleitet, der sie dann formatiert. Dies ist eine unumstößliche Regel: Eine Aktion muss vollständig von den Ansichten entkoppelt sein.
